# プレリリースで見送った項目

プレリリースは、ゲスト利用者がカードを登録・取り込みし、FSRSで復習できる最小範囲に限定する。以下は削除ではなく、上位計画へ戻して実装する項目である。

| 何を削ったか | どのフェーズの何に相当するか | 無いと何が起きるか |
| --- | --- | --- |
| タグと `card_tags` | Phase 2 コンテンツ分類 | カードを複数の横断カテゴリで整理できない。 |
| `import_batches` / `import_candidates` による重複プレビュー | Phase 2 取り込みプレビュー | 同じ内容を再度取り込むと重複カードが作られる。 |
| `tango.backup` envelope と復元 | Phase 3 学習履歴バックアップ | 学習状態（FSRSのスケジュールと履歴）を書き出して移せない。カードの書き出しは実装済み。 |
| 直前レビューのundo | Phase 3 復習取引 | 評価を押し間違えても、その場で前のスケジュールへ戻せない。 |
| ダッシュボードの所要時間と表示切替 | Phase 3 進捗・履歴 | 所要時間の目安が出ず、進捗表示を隠す設定も無い。 |
| 希望保持率の設定UI | Phase 3 学習設定 | すべての利用者が固定の0.90で学習する。 |
| カード検索と絞り込み | Phase 2 コンテンツUI | カードが増えると目的のカードを探しにくい。 |
| デッキ間のカード移動 | Phase 2 コンテンツ編集 | 作成後にカードの所属デッキを変更できない。 |
| カードのサスペンド | Phase 2 コンテンツ状態 | 一時的に出題から外したいカードも復習対象になる。 |
| デッキのアーカイブUI | Phase 2 デッキ状態 | 削除せず一覧や学習対象から隠す操作ができない。 |
| モバイル最適化 | Phase 3 レスポンシブ学習UX | 基本的な狭幅表示はあるが、実機ごとの操作性・キーボード・セーフエリアは保証しない。 |
| アクセシビリティ検査 | Phase 3 UI品質、Phase 4 リリース検証 | セマンティックHTMLとキーボードフォーカスは実装しているが、支援技術による総合検査は未実施。 |
| Playwright E2E | Phase 2〜3 E2E | ブラウザを跨ぐ一連の操作はコンポーネント/API/DBテストの組合せでしか保証しない。 |
| App LXCとDB LXCの分離 | Phase 4 本番構成 | 単一LXC障害でアプリとDBが同時停止し、DBネットワーク分離も弱い。 |
| pgBackRestとPITR | Phase 4 バックアップ | 復旧点は日次 `pg_dump` 時点までで、最大24時間分を失う可能性がある。 |
| Uptime KumaとZabbix | Phase 4 監視 | 自動死活・容量・DB・バックアップ監視がなく、障害検知が利用者報告頼みになる。 |
| Discord通知 | Phase 4 通知 | 障害・容量・バックアップ遅延・復旧を自動通知できない。 |
| コンテナイメージのdigestピン留め | Phase 4 サプライチェーン固定 | タグの指す内容が将来変わる可能性を完全には排除できない。 |
| バックアップtimerの配布 | Phase 4 定期ジョブ | `backup.sh` は1日1個に制限するが、LXC側でcronまたはsystemd timerを設定しないと自動実行されない。 |

| 何が足りないか | どう困るか | 想定する対処 |

| 既存アカウント同士の統合 | Google と GitHub で別々にアカウントを作ってしまうと、後から 1 つにまとめられない。`link-social` は「ログイン中のアカウントへ未使用のプロバイダを足す」操作であり、既に別ユーザーへ結び付いたプロバイダは受け付けない。 | 統合フローを設計する。両アカウントの所有を確認したうえで、学習データを移送して片方を閉じる。上位仕様の初回リリース除外（非空アカウントへの復元）と整合を取る必要がある。 |
| 学習の評価の実機確認 | 評価ボタンを押した結果が期待どおりか、実ブラウザで未確認。 | デモデッキで 1 枚評価し、`review_events` に記録され `card_schedules` の次回期限が進むことを確認する。 |

## 次にやること（順序）

1. **実 OAuth シナリオ 2・3 の確認** — 連携と解除。GitHub 側に本番のリダイレクト URI を登録してから
2. **学習の評価の実機確認**
3. **OAuth シークレットのローテーション完了**（上の「運用の未処理」の順序を守る）
4. **基盤の本番化** — App/DB LXC 分離、pgBackRest と PITR、監視、**バックアップ**
5. **デザイン工程** — 現在の UI は急ぎで作ったものなので、本番向けに作り直す

**人に使ってもらう前にバックアップが動いている必要がある。** 4 を後回しにしたまま利用者を増やさない。


## 実装済み: ゴミ箱の復元（2026-09-13）

承認どおり `GET /api/trash` と復元 2 本、`/trash` 画面、保持期限 30 日の物理削除（`purge-expired-guests` へ相乗り）まで入れた。削除時の確認文言も「ゴミ箱から30日以内なら戻せます」へ直した。

## 実装済み: ダッシュボード集計（2026-09-14）

`GET /api/study/dashboard` を足し、デッキ一覧の先頭に当日の完了枚数、連続学習日、残りの合計、直近7日の活動量、次回期限を出す。集計は追記専用の `review_events` から導出し、取り消しは差し引きで扱う。連続日数の走査は365日で打ち切る。

所要時間の目安（直近100件の応答時間の中央値）と、進捗を隠す設定は入れていない。前者は応答時間の記録が揃ってから、後者は設定画面を作るときにまとめる。

## 実装済み: デッキの書き出し（2026-09-14）

`GET /api/decks/:deckId/export` を足し、カード詳細から取り込みと同じ `tango.content` v1 の封筒で保存できるようにした。書き出したものはそのまま取り込み直せる。上限は取り込みと同じ 10,000 枚で、超える場合は分けるよう促す。

学習状態まで含む `tango.backup` は入れていない。仕様では復元先を空の principal に限る設計で、復元側を作らないと片道の形式になるため、バックアップ工程とあわせて実装する。

## プレリリースで残す代替策

- 削除は論理削除で行い、ゴミ箱から 30 日以内なら戻せる。
- 取り込みは全件検証後に一括作成し、同じ入力を再実行すると重複することを運用上の注意とする。
- 復習取引は楽観ロック、冪等キー、追記専用イベントを省略しない。
- 日次 `pg_dump` はJSTの日付ごとに1個だけ原子的に保存し、別障害ドメインへの複製は運用側で行う。
