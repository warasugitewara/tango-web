# 本番化の計画（2026-09-14 時点）

プレリリースは単一 LXC 上の Docker Compose で動いている。人に使ってもらう前に、
**壊れたときに戻せること**を先に成立させる。順序はこの文書の並びどおり。

現状の構成と手順は README の「プレリリース配置」にある。ここでは足りないものだけを書く。

## 1. 復元が成立していること（最優先・実機作業）

`backup.sh` で毎日 dump は取れるが、**復元を一度も試していない**。試していない
バックアップは、動く保証が無いという意味でバックアップではない。

- `infra/pre-release/restore.sh` を追加した。既定では `tango_restore_<日付>` という
  別データベースへ復元するため、本番に触れずに試せる。**まだ実行していない。**
- 2026-09-19 に実機を確認したところ、**バックアップは1件も存在しなかった**。
  `/var/backups/tango` 自体が無く、root の cron も systemd timer も未設定で、
  README の手順3が一度も実行されていなかった。稼働開始から約1か月、
  実データ（デッキ・カード・学習履歴）を抱えたまま無保護だった。
- 同日、初回の dump を取得した。以後はこれが最後の復旧点になる。
- 手順は README の「4. 復元を試す」。
- 通したら、所要時間と結果をこの文書へ追記する（RTO の実測値になる）。

判定: 直近の dump から復元でき、テーブルが揃い、アプリを向けて起動できること。

## 2. 取得の自動化と置き場所（実機作業）

初回 dump は手で取った。**定期実行はまだ無い**ので、翌日以降のバックアップは存在しない。
cron か systemd timer で `backup.sh` を毎日回すことが、復元の検証より先に効く。

置き場所も同じ LXC の `/var/backups/tango` だけ。LXC ごと失うと dump も消える。

- 別障害ドメインへ複製する。Proxmox Backup Server か NAS。
- 保持は仕様どおり daily 7 / weekly 4 / monthly 6。
- 複製の失敗を検知できるようにする（4 の監視と合わせる）。

## 3. App / DB の LXC 分離

仕様の目標構成は App LXC と DB LXC の2台で、PostgreSQL は内部インターフェイスのみ、
Proxmox Firewall で App LXC の固定アドレスからの 5432 だけを通す。TLS は
`sslmode=verify-full`、認証は SCRAM-SHA-256。

移行は「新しい DB LXC を作る → dump を復元 → App の `database_url` を差し替える →
旧 DB を一定期間残す」の順。切り替え前に 1 の復元手順で検証した dump を使う。

作業前に必要なもの:
- DB LXC の固定アドレス
- サーバ証明書（内部 CA でよい）と、App 側へ置くルート証明書
- 切り戻し手順（`database_url` を旧 DB へ戻すだけで済む状態を保つ）

## 4. pgBackRest と PITR

dump だけでは復旧点が最大24時間前になる。仕様の目標は RPO 15分 / RTO 2時間。

- WAL を別障害ドメインへ継続アーカイブし、週次フル＋日次差分。
- リポジトリは DB LXC 自身や同じローカルストレージに置かない。
- 四半期ごとに隔離インスタンスへ復元して、所要時間と結果を記録する。

これは 3 の分離後に入れる。単一 LXC のまま入れても、置き場所の要件を満たせない。

## 5. 監視と通知

- Uptime Kuma: Tunnel 越しに `/health/live` `/health/ready` と OAuth 開始パス。
- Zabbix: LXC 資源、コンテナ、PostgreSQL の接続数・長時間クエリ・容量、WAL 遅延、
  バックアップの鮮度、cloudflared、メンテナンスジョブの結果。
- Discord へ即時通知するのは、停止・DB 未 ready・バックアップ遅延。容量と証明書は warning。
  復旧通知も送る。

「バックアップの鮮度」を監視対象に入れるのが要点。1〜2 が動いていても、
止まったことに気付けなければ同じこと。
